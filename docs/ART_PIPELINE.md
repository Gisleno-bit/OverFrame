# Art pipeline: Blender → `.glb` → OVERFRAME

OVERFRAME renders its fighters and stages in 3D from **segmented rigs**: a
hierarchy of rigid parts, one per bone, animated procedurally from the
simulation's own frame data. There is no skinning and no imported animation.
That is deliberate:

* it keeps the whole render layer a *function of the sim state* (rollback-safe,
  deterministic, replayable);
* it makes a fighter cheap: ~1–3k triangles, no per-vertex weights;
* it maps 1:1 onto a Blender scene of parented objects, so an artist needs no
  add-on and no custom exporter — File ▸ Export ▸ glTF 2.0 (`.glb`) is the
  whole pipeline;
* the game ships with procedural placeholder models for every fighter and stage,
  so art is never on the critical path.

Everything in this document must be **original work** (see `LEGAL.md`). Do
not start from ripped models, and do not aim for a lookalike of an existing
character or stage.

## 1. Get the reference rig

```bash
overframe --export-glb kestrel kestrel.glb      # also boulder, viper
overframe --export-glb lattice lattice.glb      # also meridian, tidegate
```

That writes the exact skeleton the game uses — bone names, proportions, and
the current placeholder parts — as a `.glb` you can open in Blender
(File ▸ Import ▸ glTF 2.0). Model over it; keep the object names.

## 2. Scene rules for a fighter

| Rule | Why |
|---|---|
| One **object per bone**, parented in the standard hierarchy (below). No armature, no modifiers that need evaluation at export (apply them). | Each object becomes a rigid part of that bone. |
| Object names = bone names: `root`, `hips`, `spine`, `chest`, `neck`, `head`, `upper_arm_r`, `forearm_r`, `hand_r`, `thigh_r`, `shin_r`, `foot_r`, and the `_l` mirrors. Extras (`crest`, `tail1`…) are free-form. | The shared animation drives the standard names; missing bones are simply skipped. |
| Origins at the joints: an arm part's origin is the shoulder; a shin's origin is the knee; limbs hang **down (-Y)** in the rest pose. | Rotations pivot about the joint; `+Z` swing moves a hanging limb's tip forward. |
| Rest pose with **zero rotation and unit scale** on every object; only translation. | Bone axes stay world-aligned, which the animation keys assume. If you leave rotation/scale, the importer bakes them into the mesh (works, but harder to reason about). |
| The character faces **-Y** in Blender (Blender's front view, Numpad 1, shows the face). | Blender exports -Y as glTF +Z; the game turns that into its +X facing. |
| **1 Blender unit = 1 game unit.** Fighters are ~30 units tall (Kestrel 30, Boulder 36, Viper 27). | Hitboxes and platforms are in the same units. The importer can also rescale to the character's collision height, so a 3 m model still works. |
| Feet on the floor: the lowest vertex at `y = 0` in the rest pose. | The sim's position is the feet. |
| Budget: ≤ 3,000 triangles per fighter, ≤ 200 per part. Flat-shaded, low-poly reads best with the toon lighting. | Everything is re-lit on the CPU each frame. |

Standard hierarchy (offsets are yours to set):

```
root
└─ hips
   ├─ spine ─ chest ─ neck ─ head ─ (crest, hood, …)
   │           ├─ upper_arm_r ─ forearm_r ─ hand_r
   │           └─ upper_arm_l ─ forearm_l ─ hand_l
   ├─ thigh_r ─ shin_r ─ foot_r
   ├─ thigh_l ─ shin_l ─ foot_l
   └─ (tail1 ─ tail2 ─ …)
```

`_r` is the side toward the camera (+Z) when the fighter faces right.

## 3. Materials = palette slots

Colours are **not** baked into the model. Each material's *name* selects a
palette slot, and every fighter has six palettes (`src/model/palettes.rs`):

| Material name | Slot | Typical use |
|---|---|---|
| `primary` (`main`, `body`) | 0 | main body colour |
| `secondary` | 1 | chest plate, greaves, scarf |
| `accent` | 2 | crest, fins, boots, cracks |
| `skin` | 3 | face / exposed parts |
| `dark` | 4 | joints, gloves, belts |
| `glow` (`emissive`) | 5 | eyes, cores — drawn unlit |
| `light` | 6 | pale trims |
| `extra` | 7 | spare |

Prefixes and Blender suffixes are ignored: `M_accent`, `mat_glow.001` and
`Accent2` all work. A material with any other name falls back to `primary`.
Base colour in Blender is only for your own preview.

Textures are not sampled on fighters (the stylised look is flat colour +
lighting). Stage surfaces use a procedural tile texture and box-projected UVs
generated by the engine; UVs you export are kept but currently unused.

## 4. Install and test

Put the file where the game looks:

```
<game folder>/assets/characters/kestrel.glb      # boulder.glb, viper.glb
<game folder>/assets/stages/the-lattice.glb      # meridian.glb, tidegate.glb
```

or point `OVERFRAME_ASSETS=/path/to/assets`. On start the game prints
`assets: loaded …` (or why it ignored a file) and uses your rig with the same
animation, palettes and secondary motion as the placeholder. Quick loops:

```bash
overframe --versus kestrel,viper,tidegate                # play with it
overframe --demo kestrel,viper --screenshot k.png --at 60 # headless-ish check
```

`cargo test --features gltf` includes an export → import round trip of every
shipped fighter, so the importer is exercised in CI.

## 5. Stages

A stage `.glb` is *dressing*: everything in it is drawn near the play plane
with the stage's lighting. Collision always comes from `src/sim/stage.rs`, so
platform tops, ledges and blast zones never depend on art. If the file has an
object named `slab`, the procedural main platform is not drawn (your slab
replaces it visually — keep its top face at the platform height, `y = 0` for
the shipped stages, and its front face at `z ≈ +42`). Material names map to
the stage palette (`primary` slab top, `secondary` sides, `accent` lip,
`skin` soft platforms, `glow` strips, `light`/`extra` decor).

## 6. What the engine animates

You do not author animations. From the fighter's state each frame the game
builds a pose (`src/model/anim.rs`): stance with breathing, walk and run
cycles, crouch, jump-squat squash and take-off stretch, rising / falling /
fast-fall poses, shield, rolls and tumbles, ledge hang, knockdown, throws, and
for every attack a **wind-up → strike → recover** timeline driven by that
move's startup/active/endlag with the striking limb aimed at the hitbox. Extra
bones get per-character secondary motion (`characters.rs::secondary`):
Kestrel's scarf and tail feathers, Boulder's orbiting stones, Viper's tail
wave and hood flare. If you add extras with new names, add a few lines there.

Animation viewer: `overframe --anim kestrel` cycles every state and move on a
pedestal so you can check a model in each pose.

## 7. Checklist before submitting a model

- [ ] Original design; no reference to existing characters/stages (LEGAL.md).
- [ ] Object names match; rest pose has zero rotations; feet at y = 0.
- [ ] Faces -Y in Blender; ~30 units tall (or rely on auto-fit).
- [ ] Materials named by slot; looks right in all six palettes.
- [ ] ≤ 3k triangles; exported as `.glb` with *Apply Modifiers*, *+Y Up*.
- [ ] `overframe --anim <name>` — no part detaches or intersects badly in any move.
- [ ] Screenshot on each stage attached to the PR.

## 8. The procedural route (art as a JSON specification)

Since v0.6.0 a fighter can also be *specified* instead of modelled: a JSON
file under `docs/art/procedural/` lists bones (name, parent, offset),
rigid pieces (`bevel_box`, `cuboid`, `ellipsoid`, `cylinder`, `plate`; position,
XYZ Euler rotation, material slot) and the lagged extras (delay, gain, limit
about Z). `src/model/procedural.rs` parses it at model-build time with strict
validation — unknown fields, unknown bones or slots, concave plates and
non-finite numbers are authoring errors — and the shared animation applies
because the standard bone names are required. The contract (units, axes,
rotation order, capsule rules, the lag algorithm, renderer order) is
`docs/art/procedural/FORMAT.md`; the exchange loop with the reviewer
(evidence branch, fixed cameras, manifest, review format) is
`docs/art/EXCHANGE.md`. Kestrel is the first fighter on this route.

Both routes coexist: an installed `.glb` under `assets/characters/` still
overrides the procedural model of that fighter.
